### The theorems that make it load-bearing

Two from `theories/.../predication-categories/prose/claims/`.

The **Belnap speech-act partition** theorem: every value in the four-bilattice partitions positing data into four illocutionary classes — asserting (𝐭), denying (𝐟), contesting (⊤), abstaining (⊥).
Writing a sentence in a record is issuing positings on the cells the sentence touches.
Each positing lands a value somewhere on the bilattice.

The **channel-theoretic speech-act** theorem: an assertive positing on cell (s, p, o) is an infomorphism that extends the truth-threshold classification by exactly one incidence.
The closure operator is a Barwise–Seligman channel that propagates truth-designations along closure-rule conditionals.
The perlocutionary effect of a speech act is the set of cells newly truth-designated under closure after the seed positing lands.

Concretely: when I write "the substrate enforces composition" in a record, I am — formally — issuing an assertive positing on the cell (substrate, enforces, composition).
The positing tries to extend the classification by adding the incidence (substrate, composition) ⊨ enforces.
The closure operator then tries to fire on consequent cells.

But what is the subject "substrate"?
In the predicate-category, entities have records that pin their identity.
There is no `code/structures/substrate.md`.
So the cell has no subject.
The infomorphism has nowhere to land.
The closure can't propagate because there's no token in the target classification to receive the incidence.

The positing *looks* like it fired — the English sentence parses, reads as an assertion.
Under the math, it landed in the abstaining class.
No new incidence.
No perlocution.
The speech act looks like work and isn't.

That is the mathematical content of jargon obfuscation: a sentence with ungrounded subject terms is a speech act that doesn't fire.

### The substrate-as-traversable-world: semioverse navigation

A separate milestone makes the MUD-metaphor technically exact.
The claim is: a typed predication graph with geography (the directory structure), inhabitants (agent persona records), physics (closure rules), and history (the event log) IS a MUD world.
When an agent connects to this world via MCP, it doesn't retrieve fragments — it navigates.
It `look`s.
It `go`es.
It reads what's in the room.
It follows exits.

A persona record carries a `current-location` cell pointing to a substrate path.
Being somewhere in the cell log means the world around you (that region of the predication graph) is contextually active.
Navigation tools return results relative to the current location.
An agent that has been in the same region for multiple sessions has a richer context picture than one making a first visit.
The location cell updates on `go` calls; the session lifecycle opens a location and restores it at next login.
Multiple personas can occupy the same location; no mutual exclusion.

The MCP server exposes three navigation tools.
`look` lists entities and exits at the agent's current location: every cell under `current-location` with type, title, and one-sentence description; every relation type leading out (`defines`, `cites`, `depends-on`, `extends`) and the count of reachable nodes per relation type; any potential agents occupying this location; any in-progress workitems in this region.
`go` traverses to an adjacent region — arguments: a relation type and a target slug or direct path; updates the `current-location` cell; returns the `look` output of the new location.
`find` is a structural query from the current location — arguments: type/predicate/value filters; returns matching objects ordered by graph distance to current-location.
Not full-text search — structural query over the predication graph.

Role-bounded capability sets gate which regions a persona can read or write.
Role records carry `authorized-regions` (path prefixes the persona can navigate and read), `write-authorized-regions` (paths the persona can write to), `forbidden-actions` (relation types the persona cannot create).

A persona in the `theory-researcher` role can navigate all of `theories/` but not write to `operations/`.
The capability gate is checked at each `go` and write call; blocked navigation returns a `⊤` cell surfaced as a boundary-violation event rather than silently dropped.

Every write by an agent emits a `closure-participation` record naming the session, the path written to, and a `delta-to-fixed-point` value.
The delta is computed by the closure runner as a lightweight graph-distance metric: after the write, how many unsatisfied predicates remain in the graph?
A write that satisfies a required predicate decreases the distance; a write that introduces a new predicate without satisfying its requirements increases it.
Working in the cell log IS participating in its closure.
Every correct write moves the predicate graph closer to its fixed point.
The agent is not retrieving information; it is contributing to the world's internal consistency.

Multiple agents active on the same cell log simultaneously use the bilattice meet for write-conflict resolution: two agents writing different values to the same predication produce values that are met (`⊓_k`) rather than last-write-wins; the meet may produce a `⊤` contradiction cell surfaced in the anomaly queue.
The closure runner's deterministic ordering means multiple concurrent writes producing no contradiction converge to the same cell-log state regardless of arrival order.

The web UI surfaces a `world-consistency-metric` — a real-time graph of the cell log's distance to its own fixed point.
Decreases as agents write satisfying predicates; increases when new unsatisfied requirements are introduced.
The metric is an absolute count of unsatisfied predicate requirements, not a percentage.

## 00:50 — plan for the toy at `prose/learning/toys/exploring-the-roadmap/`

The captain's instruction: don't keep the roadmap as a static document.
Represent it as a YAML graph whose tasks have explicit object/morphism preconditions (requires) and postconditions (adds), so the dependency DAG is derivable mechanically, missing tasks (required-but-not-added objects/morphisms) are findable mechanically, and topological ordering across the whole graph is computable.

The schema for `roadmap.yaml`:

- A top-level `phases` list.
  Each phase has `slug`, `name`, `description`, `status`.
- A top-level `milestones` list.
  Each milestone has `slug`, `name`, `phase` (slug), `capability` (the one-sentence delta after the milestone), `status`.
- A top-level `tasks` list.
  Each task has `slug`, `milestone` (slug), `description`, a `requires` block with `objects` and `morphisms` lists of slugs, an `adds` block with `objects` (each carrying a `slug` and a `description`) and `morphisms` (each carrying `slug`, `description`, `source` object slug, `target` object slug), and `capability-delta`.

The dependency edge `task X depends on task Y` is implicit: X depends on Y iff `X.requires.objects ∪ X.requires.morphisms` contains anything in `Y.adds.objects ∪ Y.adds.morphisms`.
The script computes the edges.

Three scripts under `scripts/`:

- `validate.mjs` — checks slug uniqueness across phases, milestones, tasks; checks cross-references (every milestone's phase exists; every task's milestone exists); checks morphism source/target reference defined objects.
- `find-gaps.mjs` — for every task's requires, checks whether the referenced object or morphism is added by some task; reports the ones never added — these are missing tasks to author.
- `topo-sort.mjs` — builds the task DAG from requires/adds and produces a topological ordering using Kahn's algorithm; reports cycles if any.

A `_shared.mjs` carries the loader (reading `roadmap.yaml` with `js-yaml`) and the index-building helpers (object-added-by-task map, morphism-added-by-task map).

The toy is created with an initial seed `roadmap.yaml` populated from the first two phases of the roadmap above (Boot and Operational Kernel) so the schema is concrete and the scripts have something to operate on.
The work pattern from here: read a prior-art record naming a capability, translate it into one or more tasks with explicit requires and adds, write to `roadmap.yaml`, run `validate.mjs` and `find-gaps.mjs`, repeat.
The toy grows by accretion as prior-art content is mined and translated.
